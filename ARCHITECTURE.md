# Rycon — Architecture & Implementation Roadmap

---

## Governing Principle

> **Do not build the simulation engine first. Build the data foundation that makes the simulation engine trustworthy.**

The implementation follows a strict dependency chain.
Each phase produces a testable artifact before the next phase begins.
No phase may be skipped.

## Phase 1 — Static Source Layer

**Goal:** Ingest source data without changing its meaning.

### Inputs

```text
data/raw/world_port_index/   — Pub150bk.pdf, UpdatedPub150.csv
data/raw/natural_earth/      — geographic boundary datasets
```

### World Port Index notes

- The WPI is a publication of the National Geospatial-Intelligence Agency (NGA).
- Its data reflects information available to the NGA **up to August 31, 2019**.
- Provenance and publication version must be retained on every derived record.
- The WPI code key (harbor size, harbor type, maximum vessel size, facilities, restrictions) must be preserved as source attributes.
- The WPI must remain a **raw, immutable source**. It must not be altered or collapsed prematurely.

### Architecture

```text
data/
└── raw/
    ├── world_port_index/
    │   ├── UpdatedPub150.csv
    │   ├── Pub150bk.pdf
    │   └── PROVENANCE.md          ← publication date, source, version
    └── natural_earth/
```

### Transformation

```text
raw files
   ↓
parser
   ↓
typed records (no business logic)
```

### Rule

No business logic. No field collapsing. No ID assignment. No interpretation.

### Exit condition

> Every source record can be loaded programmatically and round-tripped without field loss.

## Phase 2 — Canonical Data Layer

**Goal:** Transform source records into Rycon-owned data structures, retaining traceability to source.

### Principle

```text
source data ≠ Rycon interpretation
```

Both are retained. A canonical port carries its source attributes alongside its Rycon interpretation.

### Canonical port — minimum fields

```text
port_id              ← Rycon-generated (see Identifier Policy, RYCON_SPEC.md §5)
source_id            ← original WPI index number
name
country
latitude
longitude
harbor_type          ← preserved WPI attribute
harbor_size          ← preserved WPI attribute (S/M/L/V)
maximum_vessel_size  ← preserved WPI attribute (before A–E mapping)
source               ← "WPI"
source_version       ← "NGA Pub 150, data through 2019-08-31"
```

### WPI → Rycon vessel class mapping

The WPI `maximum_vessel_size` field informs but does not dictate the Rycon A–E class.
The mapping must be:

- documented
- centralized
- auditable

The raw WPI attribute is always preserved. The Rycon interpretation is a separate derived field.

### Identifier generation

IDs are generated by a centralized ID module (see RYCON_SPEC.md §5).
IDs are never assigned inline or in parsers.

### Exit condition

> Every canonical port can be traced back to its source WPI record by `source_id`.
> The Rycon ID is deterministic and unique.

## Phase 3 — Static Network

**Goal:** Build the maritime graph from canonical geographic data.

### Inputs

```text
Canonical ports
Natural Earth coastlines / boundaries
```

### Outputs

```text
Node   — port or intermediate maritime point
Edge   — maritime connection between two nodes
Region — closed polygon defining a geographic region (RYCON_SPEC.md §3.1)
```

### Edge minimum fields

```text
edge_id
from_node
to_node
distance
minimum_vessel_class
```

### Intermediate nodes

- Maritime edges longer than approximately 5 km are subdivided.
- Intermediate nodes are distinguishable from canonical ports.
- Intermediate nodes do not inherit port capabilities.

### Rule

At this stage: **no vessels, no clock, no cargo, no state.**

The graph is a static data structure.

### Exit condition

> Given two node IDs, the system can determine whether a network path exists between them.

## Phase 4 — Static Vessel + Routing Engine

**Goal:** Introduce the A–E vessel abstraction and compatible pathfinding.

### Vessel capability classes

```text
A  (lowest)
B
C
D
E  (highest)
```

Defined in full in RYCON_SPEC.md §8 and §9.

### Routing algorithm

Dijkstra-based shortest compatible path.

The routing engine considers:

```text
origin
destination
vessel capability
edge minimum_vessel_class
edge traversal cost
```

### Compatibility test cases

```text
Class A vessel + minimum C edge → INVALID
Class B vessel + minimum C edge → INVALID
Class C vessel + minimum C edge → VALID
Class D vessel + minimum C edge → VALID
Class E vessel + minimum C edge → VALID
```

### Movement model

```text
travel_time = distance / vessel_nominal_speed
```

Nominal speeds are deterministic per vessel class.
No weather, currents, or stochastic effects at this phase.

### Rule

**No simulation clock yet.**
Input/output is: `(origin, destination, vessel_class) → route + duration`.

### Exit condition

> Given origin, destination, and vessel class, the system returns a valid compatible route and estimated travel duration.
> Incompatible routes are correctly rejected.

## Phase 5 — Deterministic Single-Voyage Engine

**Goal:** Bridge routing software and simulation software with a single controlled voyage.

### Inputs

```text
One vessel
One cargo record
Origin → destination
```

### Lifecycle

```text
Cargo CREATED
   ↓
ASSIGNED → vessel
   ↓
LOAD_STARTED   (t = 0:00)
   ↓
LOAD_COMPLETED (t = 2:00)
   ↓
DEPARTED       (t = 2:00)
   ↓
ARRIVED        (t = computed from route + speed)
   ↓
UNLOAD_STARTED
   ↓
UNLOAD_COMPLETED
   ↓
Cargo DELIVERED
   ↓
Vessel IDLE
```

### Simulation clock

Introduced here for the first time.
Deterministic only.
No randomness.

### Event log example

```text
t=00:00  SHIP_ASSIGNED
t=00:00  LOAD_STARTED
t=02:00  LOAD_COMPLETED
t=02:00  DEPARTED
t=08:30  ARRIVED
t=08:30  UNLOAD_STARTED
t=10:30  UNLOAD_COMPLETED
t=10:30  SHIP_AVAILABLE
```

### Exit condition

> One complete voyage executes from cargo creation to delivery and vessel return to IDLE without manual intervention.

## Phase 6 — Stateful Multi-Vessel Simulation

**Goal:** Prove the simulation handles concurrent, overlapping, consecutive operations correctly.

This is the **Iteration 1 completion gate** (see RYCON_SPEC.md §22).

### Requirements

```text
3+ vessels operating simultaneously
5+ cargo records
Multiple destinations
Overlapping voyage timelines
Vessel reuse after delivery
Consecutive assignments
```

### Discrete-event engine

```text
Event queue (chronological)
   ↓
Process next event
   ↓
Update entity state
   ↓
Schedule consequent events
   ↓
Repeat
```

### State machines become operational here

Vessel:   IDLE → ASSIGNED → LOADING → SAILING → ARRIVED → UNLOADING → IDLE
Cargo:    CREATED → ASSIGNED → IN_TRANSIT → DELIVERED

Invalid transitions must be rejected (RYCON_SPEC.md §18).

### Exit condition (mirrors RYCON_SPEC.md §22)

```text
All cargoes reach DELIVERED
All expected vessels return to IDLE
Event log is chronologically ordered
No vessel traverses an incompatible segment
No invalid state transition is accepted
```

## Phase 8 — Operational Constraints

Progressive additions only. Each sub-phase has its own exit condition.

### 8.1 Vessel capacity

```text
cargo quantity vs vessel capacity check before assignment
```

### 8.2 Port capacity

```text
berths, queues, handling resources
```

### 8.3 Cargo compatibility

Some cargo may require specific vessel capabilities or port facilities.
The WPI facility attributes preserved in Phase 1/2 can support this.

### 8.4 Port queues

Two vessels competing for the same berth. This is where the simulation becomes materially realistic.

## Current Position

The repository has advanced beyond the original pre-implementation roadmap. The current workspace boundaries are:

```text
DS_System/          Demand/supply contracts, validation, in-memory store
packages/engine/    Maritime graph, routing, movement, event simulation
packages/server/    Composition root, API/WebSocket adapters, reports
packages/client/    Operator console, map, event history, report exports
data/raw/           Immutable source data and provenance
```

From the workspace root, `pnpm rycorn` starts the local API and client together.

`DS_System` does not import the engine. The server adapts DS demand records into engine cargo definitions, supplies the fleet, and maps Rycon assignment/transit/delivery events back into DS lifecycle states. Requests can be edited or cancelled while pending; after assignment their execution state is controlled by Rycon.

### Time and reporting

- `simulationTime` is elapsed modeled hours from `T+0`, advanced in event-queue order. It is not a date on the host calendar.
- `d` is the sum of `distanceKm` on the selected network edges. The router chooses the path; movement uses the configured nominal speed profile to calculate travel duration. Loading, unloading, and configured delay modifiers contribute additional modeled hours.
- `observedAtUtc` is sampled from the server host clock via `Date.now()` when an event/state is processed or published. It is provenance metadata and does not change event ordering or the modeled clock.
- `/simulation/report` combines DS demand, current cargo/vessel state, route and distance metadata, events, time observations, and system errors. The client refreshes it live and exports JSON/CSV or uses browser print-to-PDF.

### Audit findings and next work

- The server builds demand routes and connector paths from WPI ports, then screens each unique graph edge against Natural Earth 1:10m land geometry at approximately 2 km intervals. First and last port connector edges up to 100 km are exempt because WPI coordinates can lie on land. This is a coarse geometry screen, not a navigational guarantee.
- The engine router remains geography-agnostic and assumes its input graph is valid. Server-built routes are screened before entering the engine; networks constructed by direct engine callers are not.
- The continuous global scenario models 14 reciprocal illustrative trade lanes across eight Rycon market regions. Empty vessel repositioning allows a ship to reach demand at another port. It adjusts model volumes deterministically by up to ±10% between cycles and retains bounded recent shipment/event history.
- Regional assignments come from port country groupings. They are planning categories, not authoritative customs or economic regions. The WPI has no trade volumes or origin-destination matrix; all lane choices and weights remain assumptions until a sourced trade dataset is connected.
- Demand can be added or edited while the server is running. The server builds a route and connects the new port into the active route graph before handing the demand to the engine. Fleet supply can be added to an initialized engine as well.
- Movement, fuel use, port handling, and port access remain deterministic approximations. Realistic calibration requires sourced vessel-speed, fuel, port-operation, and trade-flow data. Clock metadata is not a substitute for those models.
- Display scale, marker size, and label density belong to the client and must not alter physical distance or simulation time.

The next system work is connecting sourced maritime trade and connectivity data, calibrating movement and port handling, adding route disruption and port capacity models, and validating those extensions against operational observations. Keep observed host time and simulated time distinct.

## Engine Independence Principle

> **The simulation engine is an independent product boundary.**
> The system around it supplies data/configuration and consumes results.
> The engine itself must not know whether the caller is an API, CLI, dashboard, batch job, or Python system.

```text
                 ┌─────────────────────────┐
                 │   RYCON SYSTEM          │
                 │                         │
Data ───────────►│  Data / Integration     │
                 │          │              │
                 │          ▼              │
                 │   Simulation Engine ◄────┼── Configuration
                 │          │              │
                 │          ▼              │
                 │     Results / Events    │
                 │                         │
                 └──────────┬──────────────┘
                            │
                     API / Files / Stream
                            │
                     Visualization
```

The engine must be independently instantiable and testable without Fastify, React, PostgreSQL, or any HTTP layer.

## Phase 2 — Canonical Data Layer

### Objective

Transform validated Phase 1 source records into stable Rycon-owned domain entities.
Output must be independent of WPI, Natural Earth, CSV structure, or any external provider.

### Canonical entities

```text
Port
Region
GeographicNode
```

### Canonical Port structure

```text
Rycon Port
 ├── ryconId
 ├── sourceReferences[]
 ├── geographic position
 ├── identity
 └── source metadata
```

### Business Rules

1. Every canonical port has exactly one stable Rycon ID.
2. Source IDs are not Rycon IDs.
3. Canonical models must not depend on source column names.
4. Raw data must never be modified.
5. Missing mandatory information must produce validation errors.
6. Provenance must survive every transformation.

### Out of Scope

Routing, vessels, cargo, simulation, API, visualization.

### Acceptance Criteria

* Canonical ports can be generated reproducibly.
* Every canonical port can be traced to its source.
* Canonical schemas pass automated validation.
* No source-specific logic leaks into domain models.
* Tests pass.

## Phase 3 — Static Maritime Network

### Objective

Construct the static maritime graph from canonical geographic data.

### Core Model

```text
Node
Edge
Network
Region
```

Ports are special geographic nodes. Intermediate maritime nodes are distinct from ports.

### Network Construction

```text
Canonical Ports
      ↓
Geographic relationships
      ↓
Maritime edges
      ↓
5 km intermediate-node generation
      ↓
Static network
```

### Edge Requirements

```text
edgeId
fromNode
toNode
distance
minimumVesselCapability
```

Additional metadata must be extensible.

### 5 km Intermediate Nodes

Long maritime connections are subdivided approximately every 5 km.
Must preserve: original endpoints, topology, coordinate ordering, total route geometry.
Intermediate nodes must not accidentally become ports.

### Business Rules

1. Network topology is immutable during this phase.
2. Nodes must reference valid geographic entities.
3. Edges must reference existing nodes.
4. Distances must be calculated consistently.
5. No routing decision occurs during network construction.

### Out of Scope

Vessels, cargo, dynamic routing, simulation, weather, congestion.

### Acceptance Criteria

* Network generated deterministically.
* No orphan edge references.
* Intermediate nodes correctly generated.
* Port nodes remain distinguishable.
* Network integrity tests pass.

## Phase 4 — Routing and Movement

### Objective

Create independent routing and movement capabilities.

### Vessel Capability

```text
A (lowest) < B < C < D < E (highest)
```

### Routing

Input: origin, destination, vesselCapability, network
Output: Route

Dijkstra must reject incompatible edges:
```text
vesselCapability >= minimumVesselCapability
```

### Movement

Input: Route, VesselSpeedProfile
Output: TravelDuration

```text
travelTime = distance / speed
```

### Architecture Constraints

Routing must NOT depend on: API, database, frontend, simulation engine.
Movement must NOT depend on: event queue, UI, HTTP.

### Acceptance Criteria

* Compatible routes are returned.
* Incompatible routes are rejected.
* No-path situations represented explicitly.
* Travel duration is deterministic.
* Routing and movement testable independently.

## Phase 5 — Independent Simulation Engine

### Objective

Build the Rycon simulation engine as an independent computational component.

### Engine must NOT depend on

React, Fastify, HTTP, PostgreSQL, dashboard code, frontend state, or external demand/supply implementation.

### Engine Boundary

```text

       ↓

       ↓

```

### Core Components

```text
SimulationEngine
SimulationClock

VesselStateMachine

```

### Required States

Vessel: IDLE → ASSIGNED → LOADING → SAILING → ARRIVED → UNLOADING → IDLE

## Phase 6 — Multi-Vessel Simulation

### Objective

Extend the independent engine to support concurrent logistics activity.

### Requirements

```text
Vessel A
 ├── Cargo 1 → Port X
 └── Cargo 2 → Port Y

Vessel B
 └── Cargo 3 → Port Z
```

Multiple vessels, cargoes, destinations, overlapping voyages, consecutive assignments, vessel reuse.

Events ordered by simulation time with deterministic tie-breaking.

### Engine Isolation

### Acceptance Scenario (minimum)

```text
3 vessels
5 cargoes
2+ destinations
overlapping operations
```

All valid cargo reaches destination, vessels become reusable, no incompatible segment traversed, event ordering deterministic, invalid transitions impossible.

## Phase 9 — Dynamic Conditions

### Pluggable models

```text
Base Movement + Weather Model + Current Model + Congestion Model → Effective Movement
```

Base engine must function without these models.
Stochastic models must support controlled seeds. The default scenario now wires seeded weather speed sensitivity, daytime congestion sensitivity, and port handling delay into the engine. These repeatable inputs are illustrative and are not live observations or calibrated forecasts.

## Phase 10 — Real-Time Visualization

### Architecture

```text
RYCON ENGINE (independent)
      ↓
Event Stream
      ↓
System/API Layer (Fastify)
      ↓
WebSocket / SSE
      ↓
React + TypeScript + Map visualization
```

### Visualization must display

Maritime network, ports, vessels, vessel positions, routes, cargo states, port states, simulation clock, events, alerts, completed deliveries.

### Critical boundary

The visualization is a consumer of the engine.
It must NOT: calculate routes, modify vessel state, execute simulation rules, contain business logic.

### Acceptance Criteria

* Running simulation observable on map in near real time.
* Pausing the engine pauses the observed simulation.
* Same engine runs without visualization.
* Visualization replaceable without modifying simulation logic.

The map displays engine vessels against the simulation clock. Special-class patrol markers are explicitly labeled fictional route previews and use the same clock rate; they are not included in fleet supply or route assignment.
